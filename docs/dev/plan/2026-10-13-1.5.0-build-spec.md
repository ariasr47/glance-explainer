# Build spec: 1.5.0, checked pages, upgradable pages, answers by tapping

Greenlit by Rodrigo on 2026-10-13 ("A": all three in one release). Two build lanes run in parallel worktrees; the maintainer merges, bumps the version and writes the changelog. Read this whole file before starting.

## Ground rules for both lanes

- Repository layout: see `CONTRIBUTING.md`. Each skill folder is self-contained; skills name files by paths relative to their own `SKILL.md`.
- Zero dependencies. Node 18 built-ins only. Python only for your own browser checks (`py -3`, Playwright with `pw.chromium.launch(channel='chrome')`).
- `node tools/check-repo.mjs` must exit 0 before every commit.
- If you change the `<style>` or `<script>` block of `skills/html-explainer/assets/template.html`, paste both blocks into `skills/html-explainer/assets/gallery.html` so they stay byte-identical (check-repo enforces this). Do not touch `docs/index.html`, `docs/roadmap.html` or the examples' blocks; the maintainer re-syncs them at merge.
- Plain English in docs, per `skills/html-explainer/references/writing.md`: no semicolons, no em dashes, short sentences.
- Conventional commits with a scope, for example `feat(hooks):`. No AI attribution trailer. Do not push. Do not edit `CHANGELOG.md`. Only lane 1 touches `.claude-plugin/plugin.json` (the version, step 1b).
- LF line endings. Edit with tools that keep LF.

## Lane 1: the checker runs by itself, and old pages can be upgraded

### 1a. Plugin hooks (Claude Code only)

First confirm against the official docs (https://code.claude.com/docs/en/hooks and the plugins reference) the plugin hook file location (`hooks/hooks.json` at the plugin root), the `${CLAUDE_PLUGIN_ROOT}` variable, the stdin JSON fields (`session_id`, `cwd`, `tool_name`, `tool_input.file_path`, `stop_hook_active`), and that a `Stop` hook exiting with code 2 blocks the stop and shows stderr to Claude. If the docs differ from this spec, follow the docs and say so in your report.

Files: `hooks/hooks.json` and `hooks/explainer-check.mjs` at the repository root (hooks are a Claude Code feature, so they live outside the portable skills).

Behaviour, one script with a mode argument:

| Hook | Matcher | Command | Does |
|---|---|---|---|
| `UserPromptSubmit` | none | `node "${CLAUDE_PLUGIN_ROOT}/hooks/explainer-check.mjs" turn` | Records the turn start time for this session. Silent, exit 0. |
| `PostToolUse` | `Write\|Edit\|MultiEdit` | `... explainer-check.mjs track` | If `tool_input.file_path` ends in `.html` and the file looks like an explainer page, adds the absolute path to this session's list. Silent, exit 0. |
| `Stop` | none | `... explainer-check.mjs stop` | Checks every page that this turn touched (see below). On any FAIL: prints a short report to stderr and exits 2, so the agent fixes the page before handing over. On PASS: exit 0, silent. |

- **Looks like an explainer page:** the `<html>` tag has a `data-type` attribute, and the file contains `class="answer"` or `class="ballot-card"`. Anything else is ignored.
- **Pages this turn touched:** the tracked list, plus, when `cwd` is inside a git repository, files from `git status --porcelain --untracked-files=all` that end in `.html`, look like explainer pages, and were modified at or after the turn start. This catches pages written by a script through Bash.
- **The check:** run `skills/html-explainer/scripts/check.mjs <file>` with `process.execPath`. Report the file path and only its `FAIL` lines, then one line: `Fix every FAIL, then save the page again. The checker runs again before you finish.`
- **No endless loop:** count blocks per session and turn in the state file. After 3 blocks in one turn, exit 0 and stop blocking for that turn.
- **State:** one JSON file per session in `os.tmpdir()/html-explainer-hooks/<session_id>.json`. Remove entries for files that passed. Never throw: any internal error exits 0 (a hook must never break a session). Keep the script fast: no network, no work at all for non-HTML files.
- **Windows:** paths may arrive with backslashes; normalise. Quote the command path in `hooks.json` for spaces.

Tests (run them, do not ship a test file): pipe hand-made JSON into each mode with files in a temp folder and show the exit codes for: a non-HTML file; an HTML file that is not an explainer; a failing explainer (Stop exits 2 with the FAIL lines); the same page fixed (exit 0); a fourth Stop in one turn after three blocks (exit 0); a page created by a script inside a temp git repository after the turn start (caught) and one modified before it (ignored). Then `claude --plugin-dir <a copy of the repo with the plugin name changed in plugin.json> plugin details <that name>` must list the hooks.

### 1b. Version mark

- Add `<meta name="generator" content="html-explainer 1.5.0">` to the `<head>` of `skills/html-explainer/assets/template.html`, right after the viewport meta. Not inside `<style>` or `<script>`.
- Set `version` in `.claude-plugin/plugin.json` to `1.5.0` on your branch. It reaches `main` only with the merged release.
- `tools/check-repo.mjs`: fail when the template's generator version differs from `plugin.json`'s version.

### 1c. `skills/html-explainer/scripts/upgrade.mjs`

`node upgrade.mjs <page.html | folder> [--dry-run] [--force]`

- For each `.html` file that looks like an explainer page (rule above), replace its first `<style>` block and its first `<script>` block with the current template's (read from `../assets/template.html` relative to the script). Everything else stays: content, any extra `<style>` or `<script>` blocks the page added after them, atlas `<link>`s.
- Set or update the generator meta to the template's version.
- **Know the version it came from.** Build a map from a hash of the style block plus script block to a version, for every released template: tags `v1.0.0`, `v1.1.0`, `v1.1.1`, `v1.2.0`, `v1.3.0`, `v1.4.0` (paths: before 1.4.0 the template was `assets/template.html`; from 1.4.0 it is `skills/html-explainer/assets/template.html`; use `git show <tag>:<path>`, with `MSYS_NO_PATHCONV=1` in Git Bash). Embed the map as a small constant in the script, with a comment saying how it was generated. A page whose blocks match no known version is "custom": skip it with a message unless `--force`.
- Write a backup `<page>.html.bak` before changing a file (do not overwrite an existing `.bak`; use `.bak2`, `.bak3`).
- Run the checker on the upgraded page. If the original passed and the upgraded page fails, restore the original, keep the backup, and report it.
- Output one line per file: `upgraded 1.2.0 -> 1.5.0`, `already current`, `skipped: custom styles (use --force)`, `skipped: not an explainer page`, or `restored: upgraded page fails the checker`. Exit 0 unless a file could not be read or written.
- Tests (run, do not ship): upgrade copies of the private examples is NOT allowed (they are outside this repo). Instead extract pages from history: `docs/explainers/2026-10-07-the-plugin.html` at tag `v1.1.0` and `docs/examples/playbook.html` at `v1.3.0`, write them to a temp folder, upgrade them, show the version detected, the checker result, and that the content outside the two blocks is unchanged (diff with the blocks stripped).

## Lane 2: answers by tapping

### 2a. Decision pages may end with tap-to-answer fields

- `skills/html-explainer/scripts/check.mjs`: for `data-type="decision"`, the requirement becomes: at least one `.decision`, and either a `section.ask`, or at least one `.answer-field` with exactly one `.collect` bar where every field has a `data-q`. Reuse the playbook checks (search for `data-type="playbook"` near the end of the file). Keep every other rule.
- Pattern: each chapter's `.decision` card is followed by its `fieldset.answer-field[data-kind="choice"]` (the recommended option's label has `data-rec="Recommended"`), and one `.collect` bar sits after the recap, outside the chapters.
- `skills/html-explainer/references/types.md` decision section and `references/design-system.md`: document the pattern. Gallery: in the "Ask and collect" or decision area, show one decision card followed by its answer field, with a one-line note.

### 2b. Ballot upgrades

Read `docs/dev/proposals/2026-10-13-ballot-upgrades.md` first. Build:

1. **Text options.** A `.ballot-opt` passes when it has a non-empty `.vis` or a non-empty `.detail` (a `span.detail` or `p.detail` with one plain line). Style text options so they read as cards without a picture: label bold, detail line in `--ink-soft`, same tap target size. The checker's existing warning "the .vis of option X is text alone" stays for options that have a `.vis` holding only text. Update the checker's ballot block and its message.
2. **Pick all ★.** A tray button `button[data-pick-rec]`, label "Pick all ★". It sets every unpicked single-choice card to its `data-rec` option (multi cards are left alone), updates the tally and pips like a tap would, then moves focus to Copy picks. It never changes a card the reader already picked.
3. **Consequence chip.** `data-warn="Can't undo"` on a `.ballot-opt` (and on a decision page's `.option`) shows an amber chip with a "⚠" glyph and the text, never colour alone, contrast 4.5:1 in both themes (the checker computes contrast from tokens; use existing tokens). Add `data-warn` to the translatable attributes in `skills/html-explainer/scripts/translate.mjs` (`ATTRS`).
4. **Review and note.** Inside the tray, a collapsed `details` "Review picks": one row per card, its `data-short` and the pick, or "★ (skipped)". Below it an optional one-line note field ("Anything else?"). The note, when not empty, is appended to the copied text as a last line `Note: ...` and to Copy JSON as `"note"`. The tray must still fit a 390 px phone without covering the Copy button, and with 10 cards.
5. **Short paste line.** When every single-choice card resolves to its ★ option (picked or skipped) and there are no multi cards, Copy picks gives one line: `<page title>: all ★ (recommended)`, plus the note line if any. Otherwise the current format.
6. **Source line.** An optional `p.ballot-source` under the ballot title: small, muted, for "Rules on: <plan>, <date>, <commit>".
7. **Docs.** `skills/explainer-gather/SKILL.md` ballot section: text options, `data-warn`, Pick all ★, the note, the short paste line, the source line, and the convention "put the recommended option first". `references/design-system.md`: rows for the chip, text options and the source line. `assets/i18n/ui.ja.json`: Japanese strings for "Pick all ★", "Review picks", "Anything else?", "★ (skipped)", "all ★ (recommended)".
8. **Example.** In `skills/explainer-gather/examples/ballot.html`, convert one card to text options with one `data-warn` chip, and add a `p.ballot-source`. Bring its `<style>` and `<script>` to the new template's.

### 2c. One template fix

In the template script's in-page link handler (search for "every other in-page link scrolls by script"), a link whose `href` is exactly `#` must not navigate (call `preventDefault()` and stop). Inside an embedded viewer such a click blanks the page; the ask's `.choices` links use `href="#"`.

### Lane 2 tests

- `node tools/check-repo.mjs` exits 0.
- Checker: a decision page with answer fields and a collect bar but no `section.ask` passes; one with neither fails; a ballot card with text options passes; an option with neither `.vis` nor `.detail` fails. Use temp files, do not ship them.
- Chrome at 390 and 1280 px, light and dark, on the gallery and the ballot example: no sideways scroll, no console errors. On the ballot: Pick all ★ fills only unpicked cards; the review rows match; Copy picks text is the short line when all are ★ and includes the note; the tray with 10 cards keeps Copy inside the screen on a phone (duplicate cards in a temp copy to test). Use a clipboard stub (`navigator.clipboard.writeText` override) to read what was copied.
- An embedded srcdoc frame test: clicking an ask choice with `href="#"` leaves the page in place.
