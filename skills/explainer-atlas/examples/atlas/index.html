Chapter 3 of 5, about 2 minutes

What runs when you save a page?

Before this: a page is checked many times, and the hook and CI do the repeating.

Two chains run the checker for you. The hook runs while Claude Code works. CI runs when you push.

The hook, inside one Claude Code turn

  1. Claude saves the page with Write or Edit. hooks.json:13
  2. The hook notes it if it looks like an explainer. explainer-check:54
  3. When the turn ends, the stop step asks the checker about each noted page. explainer-check:139
  4. check.mjs returns its FAIL lines. explainer-check:118
  5. A FAIL exits 2, so Claude fixes it. Three blocks at most. explainer-check:169 explainer-check:14

CI, after a push

  1. You push to main or open a pull request. ci.yml:3
  2. The check job runs check-repo on Node 18. ci.yml:19 ci.yml:21
  3. check-repo checks each shipped page, then five more things. check-repo.mjs:34
  4. On main only, and after check passes, the site job copies the shipped files into _site. ci.yml:24 ci.yml:38
  5. The Pages action deploys that folder. ci.yml:49

Take from this: both chains end at the same checker. They differ in when they run and who sees the result.

Remember: the hook runs the checker at the end of a turn, and CI runs it on every push.

Take from this: the checker owns page rules and check-repo owns repository rules. Only anchors.mjs reads an atlas's line numbers.

Show where each owner does its work

Yes. check.mjs prints FAIL lines and sets the exit code at check.mjs:586. The hook blocks the turn with exit 2 at explainer-check:169. upgrade.mjs swaps the blocks at upgrade.mjs:106. check-repo compares the gallery at check-repo.mjs:42 and checks skill paths at check-repo.mjs:55. anchors.mjs counts anchors out of range at anchors.mjs:62.

Partly. upgrade.mjs re-checks only the page it upgraded, at upgrade.mjs:137. check-repo checks only the shipped pages, at check-repo.mjs:24. check.mjs checks that an anchor has both attributes, not that the line exists, at check.mjs:336.

Remember: each failure has one owner, so a pass from one check proves nothing about another.

Chapter 5 of 5, about 2 minutes

How does it ship, and what is not live?

Before this: each failure has one owner, and CI is the last guard before the site.

A release is a short, fixed path. Users get it through the marketplace, and the site redeploys from main on its own.

  1. Bump the version. plugin.json and the template's mark move together. plugin.json:4 check-repo.mjs:76
  2. Run check-repo. Then the strict plugin validation. CONTRIBUTING.md:72
  3. Merge, tag and release. To main, a vX.Y.Z tag, a GitHub release. CONTRIBUTING.md:73
  4. Let users update. The plugin lists three skills, and the marketplace delivers it. plugin.json:13 CONTRIBUTING.md:74

Take from this: a release is four steps. The site is not one of them, because it redeploys when main changes. ci.yml:25

Dormant: the root skill shim. Parked on 13 October 2026. It returns only if someone asks to clone the repository as one skill. root-skill-shim.md:9

Target: a render flag. The roadmap adopts a browser check for December. The checker takes no such flag yet. ROADMAP.md:19
